使用者 2026-11-17：「這版先合併推上去，因為今天一整天下來你自己都不滿意，先擬下一批計畫。視覺要不要你自己跳下來作？你先上網找這兩週關於 Fable 5.2 的模型分工原則，官方有釋出過。」

## 2. 誰做視覺：官方的分工原則與主席的建議

主席 2026-11-17 讀的官方文件（都是 Anthropic 自己的頁面；Fable 5.2 的發表文日期是 2026-11-09）：

- [Prompting Claude Fable 5.2](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2)
- [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- [Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)
- [Advisor（Claude Code）](https://code.claude.com/docs/en/advisor)
- [Introducing Claude Fable 5.2](https://www.anthropic.com/claude-fable-and-mythos-5-2)

和我們有關的幾點（頁面是由讀網頁的子代理摘回來的；標「摘要」的是從被截斷的長頁面摘的，數字沒有逐字核對）：

1. **先用 Opus 5.5，不夠才換 Fable。** 多數工作從 Opus 5.5 開始；Opus 在較高推理強度仍達不到要求，才往上換 Fable。
2. **什麼該留在主代理手上**（Optimizing 頁「Combine models」，摘要）：工作超過一個 context、或能拆成互不相依的幾塊，才交給子代理；**一條前後相依的鏈、或一個 context 裝得下的工作，留在主代理**，這種情況下主代理自己用較低的推理強度做，結果比派出去好。
3. **主席的品質不會穿過子代理傳下去**（同頁的內部找錯測試，摘要；F1／每次成本）：Fable 自己做（high）0.909／$563；Fable 自己做（low）0.866／$357；**Fable 帶 Sonnet 子代理 0.833／$165**；Opus 自己做（medium）0.827／$200；Opus 帶 Sonnet 子代理 0.831／$139。也就是說，Fable 當主席派 Sonnet，成品大約是 Opus 自己做的水準。
4. 官方對「視覺、設計、看截圖反覆調整」該不該外派**沒有寫**。Choosing 頁把「看圖為主的工作流程」列在 Opus 5.5 底下。
5. 推理強度：低適合明確的小任務與子代理；中適合互動式寫碼；高適合難的、長的；高以上的收益不穩定。
6. Advisor：主模型用 Sonnet、需要判斷時去問 Fable。官方說它適合「多數回合很例行、但計畫品質決定成敗」的長任務；每一回合都需要最強模型的工作，直接換主模型。

**對照今天**：九區五個子代理共用了約 120 萬 token，每一次回來我看一眼就能指出問題（岸是島、等距的小波浪、月亮山），但那些問題要改著色器，照合約我不能動手，只能記下來再派。這正是第 2、3 點說的情況：調外觀是「看圖 → 改 → 再看圖」的一條相依的鏈，判斷在看圖的那一方，派出去之後成品只有實作者的水準。

**主席的建議**（要使用者決定）：

| 工作 | 性質 | 建議誰做 |
|---|---|---|
| 定調（§1 的第 1–5 項：岸、山、青金、山腳、霞的外觀） | 一條相依的鏈；靠看圖判斷；一個 context 裝得下 | **主代理自己做**，不派 |
| 構圖修正（第 6 項） | 五區互不相依；定調之後有明確的目標圖 | Sonnet 子代理 |
| 效能（第 7 項） | 有數字可驗 | Sonnet 子代理 |

「主代理」用哪個模型是額度問題，兩個都可行：

- **甲：我（Fable）直接做定調**，請使用者在 App 把推理強度調到 medium。好處是今天的脈絡都在這個工作階段裡（使用者的每一條指正、六次岩的失敗、參考圖看過什麼），不用交接。代價是 Fable 每個 token 比 Opus 貴（官方：Opus medium 每次的成本不到 Fable medium 的三分之二）。
- **乙：換 Opus 5.5 的工作階段照這份開案書做定調**。符合官方「先用 Opus」與全域合約「Opus 直接做視覺」；較省。代價是脈絡靠開案書與記憶傳過去，今天有幾次教訓是對話裡才講清楚的。

我的建議是**甲，但只限定調這一段**（P1–P3），做完給使用者看，之後的構圖修正與效能照舊派 Sonnet。理由：定調決定「對的樣子長什麼樣」，是整件事品質的上限，而且最吃今天累積的脈絡；範圍小（三個檔、一條鏈），用 medium 強度做，額度可控。

如果採甲，全域合約要改一條（現行寫「Fable 開案者，不寫程式」「Max5x：實作全派子代理」），提案：

> Fable 當主席時，**定調類的視覺工作**（材質、著色器外觀、靠看截圖反覆調整、前後相依的一條鏈）由主席直接做，用 medium 強度；能拆成互不相依、有明確目標圖或數字驗收的工作才派子代理。

回退：把這一條刪掉，回到「全派」。記憶 `kyoto-art-stays-with-claude` 同步更新。

## 3. 目標的樣子（定調）

參考圖（`.shots/ref/`，不提交）：`user-hatsune-suzuribako-lid.png`、`shioyama-2.jpg`（洲浜）；`user-toyama-cup-a.png`、`hirasan-3.jpg`（遠山）；`user-hatsune-three-grounds.png`（地、濃梨子地、圖案三層）。

### P1 岸與洲浜：研出，不是墊高的板

洲浜在實物上是研出蒔繪：埋在漆下、磨到和地同一個面，沒有台階。我們現在把它做成有厚度的浮雕，邊緣有台階的陰影，所以像板。

- 厚度降到接近零（只留極淺的起伏讓光有變化）；邊緣不再有接觸陰影的暗線。
- 面不是一個平的調子：金粉的密度**從一邊濃、往另一邊淡出**（蒔暈）。靠水或靠近觀者的那一邊濃而清楚，遠的那一邊化進地裡、沒有邊。每一片的濃的那一邊由構圖檔指定。
- 清楚的那一邊用一道細的金線（付描）收邊，不是暗線。
- 片與片相疊的地方，上面那一片的濃邊壓在下面那一片的淡處，靠濃淡分出前後，不靠陰影。
- 包漿規則不變（研出：面露出、輪廓內側一圈被漆蓋住；岸不加圈）。

### P2 山：面有粉、稜最亮、青金不是白的

- 山的面現在太透。稜下方的粉要夠濃（濃梨子地那一階，亮度 48–58），往山腳淡出；金山要比地明顯亮一階。
- 青金是金銀合金的粉，顏色是偏青的淡金，不是灰白。亮度放在金與銀之間，日夜都不能是畫面上最亮的東西（最亮的仍是稜線與建築的平金）。
- 山腳的鋸齒暗三角（山的楔形烘焙造成）要消掉：山腳是粉淡出到地，沒有形狀。

### P3 霞

霞（すやり霞）在實物上是金粉撒出的橫帶：兩端收尖或圓、邊是粉的疏密化開，裡面有濃淡，常壓著細的切金或金線。現在是灰褐、硬邊、平的帶。

- 顏色回到金（比地亮一階的濃梨子地），不是灰褐。
- 上下緣是粉的疏密漸變，沒有硬邊；兩端圓收。
- 銀的細條只當夾層（現有做法），保持淡。

## 5. 驗收

- **看圖**：每一包交三格並排（參考圖、修前、修後），放大兩倍，游標光移開；再看十一區日夜總覽。問的問題：岸還像不像板、哪一邊濃哪一邊化掉、金山和地分不分得開、青金是不是比稜線還亮、霞有沒有硬邊。
- **數字**：`PLATE_TONE=1` 三層不能顛倒（地 27–40、濃梨子地 46–60、圖案 50 以上）；不放大時亮度 > 75 的面積 ≤ 6%；穿插 0；切金佔比不升。
- **例行**：`npm run lint`、`npx --no-install tsx validate_data.js --strict`、`npm test`、`npm run build`；降級圖 22 張重拍並逐張看。
- **效能**：375×812、`PLATE_CPU=4`，換區最長幀與閒置幀時間不比 `1b3db65` 差 10% 以上；烘焙時間不增加（P5 的目標是拿回 40 ms 以上）。

## 6. 什麼時候停下來問

- P1–P3 做完：一定停，給使用者看定調。
- 某一項照 §3 做出來，主席自己看了仍不像參考圖，而且兩輪內找不到原因：停，附圖說卡在哪。
- 需要新依賴、要動受保護檔案、或要改岩：停。
- 合併 `main` 與 push：分開問。

## 7. 不做

不動岩（使用者說先不動）。不加部件（P4 的下京堂前淺岸除外，使用者否決就不加）。不改屋面顏色與貼金範圍、不改金片粒徑（等使用者意見）。不改 `src/data/`。
