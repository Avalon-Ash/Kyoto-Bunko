# 地著色器解耦：材質性質集中成一張表（提案）

日期：2026-11-18。狀態：**提案，等使用者決定；沒有改任何程式**。base：`claude/data-1117` @ `56fc135`。開案：Claude Opus 5.5（從主工作階段分出的工作階段）。Fable 有額度時，第 3 包的終審建議交 Fable。
依據：使用者 2026-11-17 的指正（全域合約「架構」、`AGENTS.md` §2「不做耦合」），`HANDOFF.md` §4.4a 第 2 項。本提案動到的只有 `src/studies/toji/plate/three-pack.js` 的 `MAKIE_GROUND_FRAG_GLSL`（地著色器），旁邊的既有耦合只列在 §7 回報，不擴大範圍。

## 0. 摘要（給使用者決定用）

- **現況**：地著色器用 `mat==N` 判斷材質，共 **47 行、84 個比較**。同一個材質的行為分散在 5–10 處。例如遠山金（23）分散在 10 行：起伏、塗層、暈染、大金片、遠山程序、顏色、稜線、開發視圖。另外有兩種 grep 抓不到的耦合：
  - 範圍比較（`mat>=19&&mat<=22`）依賴 `mat.js` 的編號順序。
  - 最後的 `else` 是隱含的預設值：沒列到的材質一律拿到燈的樣子。
- **目標**：每個材質一列，寫進一張 JS 表（單一事實來源）。表在建著色器字串時產生 GLSL 常數陣列。著色器只用 `mat` 當表的索引，讀出性質旗標、數值和「技法」編號。整段程序寫成每個技法一個函式，只在一個地方依技法編號分派。改完以後 `mat==N` 是 0 處，由測試守住。
- **怎麼證明畫面不變**：實測發現同一份程式拍兩次就不一樣（夜 9.15% 像素不同，最大差 66/255），因為 `uTime` 走實際時間。所以第一包是工具：固定時鐘、比對腳本、補覆蓋率的材質替換。之後每包都拍十一區日夜，再加五種視圖，跟改前逐像素比。純替換的包要零差異。
- **怎麼回退**：每包一個 commit，`git revert`。不留新舊兩條路的開關，因為開關本身就是第二個事實來源。
- **要使用者決定的**（§6 有細節）：
  1. 方向與送進著色器的方式（建議用 JS 產生 GLSL 常數）。
  2. 在任何一區都沒出現的材質路徑（3、4、13、19、20）和兩行到不了的程式，是保留還是刪。
  3. 立體部件那邊用字串判斷塗層類別的耦合，要不要接著做（§7）。

## 2. 目標架構

### 2.1 原則

- **資料**：每個材質一列，描述它在地上的樣子。分成三類欄位：
  - 旗標：暈染、分層、丘、作舊磨損、大金片、箔閃。
  - 數值：起伏增益、塗層模式與區間、大金片參數、`rise` 下限等。
  - 技法編號：要跑哪一段程序。
- **行為**：每段程序寫成一個 GLSL 函式，例如 `mTechBank(...)`、`mTechSuhama(...)`、`mTechToyama(...)`、`mTechRyusui(...)`、`mTechHirame(...)`、`mTechAogai(...)`、`mTechInlay(...)`、`mTechHill(...)`。函式只讀傳進來的欄位，不認識材質編號。
- **分派**：只有一處 `switch(T_TECH[mat])`。旗標用 `if(T_BOKASHI[mat]>0)` 這種讀表的形式。
- **改完以後的規則**：著色器裡的 `mat` 只能出現在 `T_*[mat]` 的索引裡。`node:test` 守住地著色器字串的 `mat(==|!=|>=|<=|<|>)[0-9]` 數量為 0，以後加材質只能加一列，不能加分支。
- **成對的材質照實寫**：19/20、21/22 的金銀兩邊程式碼不同（1032、1052 行），不硬塞成「換一個顏色參數」。做法是兩邊共用骨架，不同的段落拆成兩個技法編號，或者在函式裡用表的欄位選段落（例如 `tone`）。哪一種要看第 3 包實際拆出來的樣子，判斷寫在 commit 說明。23/24 主要差在常數，但 1088、1092 行的式子結構也不同，一樣照實處理。
- **預設值寫成一列**：第 0 列是「沒列到的材質」，行為等於現在 1014 行的 `else`。這樣隱含的預設值也變成資料。

### 2.2 表放在哪

新增一個純資料模組 `src/studies/toji/plate/ground-look.js`，不 import three，`node:test` 可以直接測。內容：

- 技法的列舉 `TECH`、塗層模式的列舉 `COAT_MODE`、欄位的預設值。
- `GROUND_LOOK`：`MAT → {tech, tone, coat:{mode, field, lo, hi, gain}, relief:{ch, chRidge, lh}, flags:{…}, flake:{…}, …}`。每一個 `MAT` 值都有一列。
- `groundLookGlsl()`：產生 `const int T_TECH[N]=int[N](…)`、`const float T_CH[N]=float[N](…)` 這類常數陣列，給 `MAKIE_GROUND_PARS_GLSL` 插進去。

為什麼不直接併進 `MATERIALS`：`MATERIALS` 是 three 網格用的 `MeshPhysicalMaterial` 參數，降級圖也讀它的 `paint`。分開放，降級圖就完全不受影響。如果使用者偏好「一個材質一列、所有面向都在同一列」（ECS 的元件寫法），可以改成每列加一個 `ground:` 元件，代價是降級圖也要納入驗收（§3.3）。這點列在 §6 給使用者選。

### 2.3 表怎麼送進著色器：三條路

| 做法 | 好處 | 風險 | 結論 |
|---|---|---|---|
| **A. JS 產生 GLSL 常數陣列** | 同檔的 `COAT`、`DENSITY` 已經這樣插值；不占 sampler 或 uniform；常數是編譯期的值，有機會逐位元相同 | 改表要重新編譯（表是靜態資料，可以接受）；ANGLE／D3D11 對常數陣列的動態索引效能要量 | **建議** |
| B. DataTexture（每個材質一列，RGBA32F） | 執行中可以調 | 地的片段著色器已經用了 6 張自己的貼圖，加上 three 的陰影與環境貼圖，手機上 16 個 sampler 的餘量要先查；多一次取樣 | A 的效能不及格時的備案 |
| C. uniform 陣列 | 執行中可以調 | 29 列 × 十幾個值會吃掉幾十到上百個 vec4，`MeshPhysicalMaterial` 本身已經用很多，手機的 224 vec4 下限不夠穩 | 不建議 |

做法 A 的注意事項：
- **數值序列化不能用 `toFixed`**。`COAT_GLSL` 現在用 `toFixed(3)`，會截掉第三位以後的小數，現有的值剛好都不超過三位才沒出事。產生器要用能還原同一個數的寫法（`String(v)`，整數補 `.`），並由測試檢查 `Number(literal) === v`。
- `mat` 來自一個位元組，索引前要夾到 `[0, N-1]`；超出的值走第 0 列。

## 3. 怎麼證明畫面不變

### 3.1 先量到的事實：拍兩次就不一樣

用同一份程式（`56fc135`）、同一個 job，南區拍兩次，再用 scratchpad 裡的臨時比對腳本（zlib 解 PNG，沒有新增依賴）比較：

| 條件 | 夜：不同像素 | 夜：最大差 | 日：不同像素 | 日：最大差 |
|---|---|---|---|---|
| 現在的 `plate-shot.mjs`（`night-still`／`day-still`） | 9.15% | 66/255 | 0.17% | 13/255 |
| 注入固定時鐘（`performance.now = () => 60000`） | 1.59% | 30/255 | 0.05% | 6/255 |
| 固定時鐘，只算差 >2 級的像素 | 305 px，集中在兩個角落 | | 1 px | |

原因：`-still` 只停部件的動作，`uTime` 仍然是 `performance.now()`（`study.js:438`、`three-renderer.js:903`），流水的線（1139 行起）和箔閃（1019 行起，`uTime*9`）每次拍的相位都不同。固定時鐘以後，剩下的差可能來自：
- 彈簧的步長。`f.time` 不動時 `dt` 退回 `.016`，結果跟渲染了幾幀有關。
- 游標軌跡用的是事件時間戳。
- 繩子的物理。

**結論：不先做工具，截圖比對證明不了任何事。**這是第 0 包。

### 3.2 第 0 包要做到的工具

1. **固定時鐘**：`plate-shot.mjs` 加 `PLATE_CLOCK=<ms>`，用 `Page.addScriptToEvaluateOnNewDocument` 在頁面載入前固定 `performance.now`（上表第二列就是這樣量的）。剩下的雜訊源（彈簧步數、軌跡時間戳、繩子）逐一找出來、固定住。目標是同一份程式拍兩次 **0 個像素不同**。
2. **比對腳本** `scripts/plate-diff.mjs <dirA> <dirB> [--noise <dirA2>] [--tol N]`：
   - 用 node 內建的 zlib 解 PNG，不新增依賴。
   - 每張圖輸出 JSON：不同像素數、占比、最大通道差、超過容許差的像素數。
   - 另外輸出一張差異熱圖。
   - 有 `--noise` 時，把 A 與 A2 的差異當雜訊遮罩，只回報遮罩外的差異。
3. **覆蓋率補拍**：dev 專用的 `?matSwap=21:19,22:20,2:3,2:4`，上傳 ident 圖時替換材質值（`three-renderer.js:598` 附近，只在 `import.meta.env.DEV` 下生效）。用現有的洲浜和丘的形狀跑 19、20、3、4 的程式，讓沒出現的材質也有像素可比。`fine.g` 的意思不同（堤是高度、洲浜是粉的厚度），畫面不會好看，但每段程式都會跑到，比對的是改前改後同一張替換圖。13 走不到地的 ident，用 `1:13` 替換一小塊即可。
4. **覆蓋率表**：§1.5 的指令寫成腳本或寫進文件，每包驗收時輸出一次。

### 什麼時候停下來問

- P0 做不到零雜訊，雜訊遮罩也不穩（同一份程式拍三次，遮罩彼此差很多）：附數字停下，問使用者能不能接受只用開發視圖與遮罩規則驗收。

## 6. 要使用者決定的

1. **方向**：材質性質集中成 `ground-look.js` 一張表，著色器用產生的常數陣列讀表（做法 A），技法函式加上一處分派。同意的話照 P0–P3 做。
2. **表放哪**：建議獨立模組，降級圖不受影響。另一個選項是每列併進 `MATERIALS` 當 `ground:` 元件，一個材質的所有面向在同一列，代價是降級圖也要驗收。
3. **死路徑**：
   - 3、4、13、19、20 在十一區的地上都沒出現。13 走不到地的 ident 圖，19、20（堤）目前沒有任何一區用。
   - 1010、1011 兩行永遠到不了。
   - 建議到不了的兩行在 P3 刪除（行為不變）；材質路徑先保留，用 `?matSwap` 證明行為不變，以後要不要刪另外決定。
4. **P4**：要不要接著把立體部件那邊的字串判斷也收進同一張表（§7）。
