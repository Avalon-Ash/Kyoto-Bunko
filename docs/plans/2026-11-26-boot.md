## 1. 目標與判讀

- **目標**：溫快取、CPU×4、正式建置，`perf-home --taps` 按鍵最長等待 ≤ 200 ms。像素不變，冷快取不退步。
- **附件的「忙碌段」不等於單一任務**：第 5、6、7 段裡已有讓出點，只是 `scheduler.yield` 的續作緊接著跑。真正的單一長任務只有三處：
  - 第 3 段：`renderer.js:112` 的 `.then`，405 ms。
  - 第 4 段：一次 `stepBuild`，391 ms。
  - 第 8 段：一次 idle 步，296 ms。
- **11/25 的 224 ms 與上面三處對不上**：可能是取樣器開銷，也可能是 taps 的時間窗沒蓋到這幾段。P0 先釐清。
- **內部餘裕**：單一任務 ≤ 120 ms（依 P0 的非 profile 長任務清單）。這是留給機器慢 1.7 倍的日子，不是驗收門檻。

| 4 | 做（P1＋P3） | 單一任務 391 ms |
| 8 | 做（P3） | 3 秒後使用者最可能正在按 |
| 7 | 做（P4），便宜的部分 | 兩個任務約 140、180 ms，慢機日會破 200 |

| 6 | 不做 | 四個步驟各 ≤ 62 ms，已由讓出點隔開 |
| 2 | 先不做 | 166 ms（含取樣開銷），低於門檻。`syncTrack` 自身 81 ms 疑似強制重排，我沒看到 `study.js`，列入 P5 候選 |

### 2.1 構圖檔入口（第 4 段）

- **寫法**：十一區都把 `return [...a(), ...b()]` 改成步驟清單 `[() => a(), () => b()]`，順序逐項照舊，包進唯一的 `composition(steps)`（新檔 `plate/compose.js`）。
- **相容**：回傳值仍是可呼叫的函式，呼叫結果與今天的陣列相同，所以 `PLATES[ward]()` 與所有既有呼叫者不用改。步驟清單另外掛在 `.steps` 上。
- **唯一的分步執行者**：`composeInSteps(fn, canYield)` 是生成器，累計時間超過切片預算才 `yield`。
- **切片預算只定義一處**：`ward-build.js` 新增 `TASK_SLICE_MS`，註明它依賴 50 ms 長任務門檻。`bake.js` 的 `RASTER_SLICE_MS` 改成讀它。
- **超預算的單一步驟**：`crags(ROCKS)` 在 Node 裡 55 ms，×4 就超標。改成每個岩群一步 `() => crags([rock])`。前提是 `plate-parts-hash --check` 不變。若 `crags` 有跨群狀態使雜湊改變，就退回單步，把問題列入 P5，不改造形。
- **中京的 `moatWall`**（Node 74 ms）同樣超標，只影響預建，列入 P5。

### 2.2 `createThreeRenderer` 分步（第 3 段）

- **切法**：函式本體改成設置生成器，在四處 `yield`：
  1. `WebGLRenderer`＋PMREM 之後。
  2. `bakeFlakeNormal`＋`bakeStampTexture` 之後。
  3. `buildBox` 之後。
  4. 盒材質與 mesh 之後。
- **驅動**：直接用 `ward-build.js` 的 `finishBuildInTasks`／`cancelBuild`，slot 形狀相同，不新增讓出程式。第一個 `await` 順便把 789 kB 的模組求值和啟動拆成兩個任務。
- **`renderer.js` 的合約**：
  - `loading` 維持 true 直到設置完成，才設 `plate` 並呼叫 `setMesh(ward)`。
  - `pending()` 仍是唯一判斷。期間的降級圖佔位、`data-renderer='webgl'`、`setMesh` 只記 ward，都是現有行為（0018）。
  - 設置丟錯仍走 `.catch → fallback(error, 'start')`（0022）。
  - `dispose` 時 `cancelBuild`，由生成器的 `finally` 釋放已建資源。dev 的 StrictMode 會實際走到這條路。
- **風險**：佔位期間 `renderer.js` 的原生 `clear()` 會插在設置步驟之間，three 的狀態快取可能失準。設置結束時呼叫 `renderer.resetState()`，並以像素比對把關。

### 2.3 `getProgram` 分攤（第 7 段）

- **提前編譯盒與地**：設置完成後立刻 `compilePrograms(boxGroup, scene)`。地與盒的程式不依賴區，可與首盤建造並行。
- **閘門不變**：啟用時仍對整個場景 `compileAsync`（0018），那時只剩區的程式要處理。`compiled` 的語意不變。
- **冷快取**：地著色器會提早約 1 秒開始編，預期只會更早出實景。用 `?cold` 驗一次。
- **首幀 `render` 147 ms**：我推測是貼圖上傳加上陰影深度程式，沒有驗證。P4 先用 profile 確認。若是貼圖，建造完成後照 `warmEntry` 的做法逐張 `initTexture`，每張之間讓出。若是別的，回報後再定。

### 2.4 預建單步上限（第 8 段）

- **細步給所有建造**：拿掉「細步只給前景」的 `canYield` 區分。同步路徑只是多跑幾次 `next()`。
- **idle 回呼**：有 deadline 時連跑到 `timeRemaining()` 用完，沒有 deadline（`setTimeout` 後備）時每次一步。
- **單步上限**：等於 `TASK_SLICE_MS` 加上最大的單一構圖步驟。
- **代價**：鄰盒預覽可能稍晚出現（0020）。P3 要量並回報。

## 4. ADR

- **0027，取代 0026**：
  - 讓出與切片預算（`TASK_SLICE_MS`）只在 `ward-build.js` 定義。
  - 渲染器啟動也分步，期間算在 `loading` 內。
  - 細步適用所有建造，預建依 idle deadline 連跑。
  - 構圖以 `composition(steps)` 為唯一入口。
  - 回傳合約、取消、失敗走 `fallback`，都照 0026 重述。
  - P3 完成時由主席寫。
- **0028，補充 0018，不取代**：盒與地的程式在首盤建造期間先編，啟用時的整場景編譯仍是唯一閘門。P4 完成時寫。是否併入 0027，依 `docs/adr/README.md` 的規則決定。

## 5. 停損

- **達標即停**：P3 後連續 2 輪（共 6 次載入）按鍵最長都 ≤ 200 ms，且校準顯示機器不是特別快。P4 只在第 7 段仍有任務超過 120 ms 時做，P5 同理。
- **P4 後仍超過 200 ms**：停，把長任務清單交給使用者。可選的只剩第 1 段或 Worker，Worker 已結案，不自行重開。
- **立即回報使用者的情況**：
  - 部件雜湊改變，或像素差異無法歸零。
  - 首盤 ready 變慢超過 10%。
  - 預覽明顯變晚。
  - 與 0019／0022 衝突。
  - 同一檢查失敗兩次。
- **校準**：校準比基線慢超過 1.3 倍的那一輪，數字照記，但不當作達標或失敗的依據，改天重量。
